# AgentOwl 运行手册

## 1. 部署与身份

应用按单团队、单宿主部署。Compose 中持久数据都位于同目录 `./data`；Nginx 独立运行在宿主机。

1. 使用普通部署账号执行 `make init`，检查 `deploy/.env` 中的 `APP_UID/APP_GID` 与目录属主一致。
2. 生产配置 `PUBLIC_URL=https://实际域名`、`AUTH_MODE=oidc`、`OIDC_ISSUER`、`OIDC_CLIENT_ID`、`BOOTSTRAP_EMAIL`、`BOOTSTRAP_SUBJECT`。身份源回调地址为 `PUBLIC_URL/auth/callback`。
3. 填写 `deploy/data/secrets/oidc_client_secret`。管理员必须提前提供 OIDC 的稳定 subject；其他用户由管理员在成员页面添加。不会根据邮箱自动授予管理员。
4. 运行 `make up`。检查迁移成功、宿主 `http://127.0.0.1:8080/health/ready` 和 Web 登录页；健康检查路径直接访问 API，不经过 Web 反向代理。
5. 按 `deploy/nginx.example.conf` 配置宿主 HTTPS、域名和证书。默认 Web/API 宿主端口为 `3000/8080`；若修改 `WEB_PORT/API_PORT`，同步 Nginx 上游和健康检查地址。内部 `8081`、Runner `8090` 与数据库不映射到宿主公网；禁止转发 `/internal/`。

本地登录仅用于受控开发/内部安装，密码至少 12 字节。Cookie 包含 HttpOnly、SameSite=Lax；HTTPS 时使用 Secure。写请求需要 CSRF Token。停用成员或更新授权会撤销其已有会话。

角色为 `admin`、`developer`、`oncall`、`knowledge`、`viewer`，可赋多个角色。渠道和仓库授权使用系统 ID；`*` 表示管理员明确授予所有资源。卡片中的平台用户不会自动获得 Web 权限。

## 2. 飞书/Lark

在“设置 → 平台账号”的“飞书 / Lark 机器人”入口点击“添加飞书 / Lark 账号”：

- 选择飞书或 Lark，填写账号名称、App ID、应用所属租户标识和 App Secret。
- 开启当前 v2 HTTP 事件，回调地址为 `PUBLIC_URL/hooks/{provider}/{connector_id}/events`。没有公网或只能配置一个回调入口时，卡片按钮也可继续发到 `/events`；如平台支持单独配置卡片按钮回调，也支持 `PUBLIC_URL/hooks/{provider}/{connector_id}/actions`。
- 在飞书开放平台的“事件与回调”中获取 Verification Token（验证事件所属应用）和 Encrypt Key（解密并验证请求），填入平台账号，完成平台 challenge 和验签。只使用手动或定时历史同步时无需配置这两项；主动事件推送需要飞书可访问的请求地址。对普通群消息、@、历史、话题以及外部群权限逐项在目标租户确认。
- 保存后点击“检查接入”。在“设置 → 消息渠道”中选择该平台账号，填写允许接收消息的群 `chat_id`。平台推送的 P2P 私聊消息不会自动新增消息渠道，会按事件里的 `chat_id` 和发送者归入私聊虚拟会话并可直接回复；消息渠道列表只维护群组或仓库等固定接收范围。未登记或已停用的群渠道不会采集。先选择“仅生成草稿”，确认质量后再启用自动回复策略。
- 用户在“个人中心 → 飞书账号”完成授权绑定；管理员也可在“设置 → 身份绑定”维护应用内 Open ID 与团队成员的映射。开发和审批卡片检查成员当前的角色、渠道、仓库及版本。

启用飞书登录与身份绑定：

1. 在飞书或 Lark 应用的安全设置中登记 `PUBLIC_URL/auth/lark/callback`，发布应用并将使用者加入应用可用范围。个人中心的“应用配置”可复制本站完整回调地址。
2. 在“设置 → 平台账号”开启该应用的“飞书登录与绑定”。
3. 用户先用已有账号登录 AgentOwl，在个人中心选择应用，跳转飞书确认账号。绑定完成后，登录页可直接使用该应用登录，卡片操作也归属同一个成员。

身份按 `(provider, app_id, open_id)` 匹配。系统不按姓名、邮箱自动合并账号或创建成员，也不会因绑定提升角色。每个成员在同一应用内绑定一个账号；重复绑定需要先解绑。解绑会撤销由该绑定建立的会话；停用成员、绑定或应用登录也会使相关登录失效。唯一登录方式不能自行解绑。授权中的用户 Token 仅用于读取本人身份，不保存、续期或交给模型；消息、文档和通知继续使用应用身份及已配置的资源范围。

要通过长连接接收群里 @ 机器人的消息：在平台账号启用“飞书长连接”，确保 App ID、App Secret 和应用所属租户标识正确，并点击“检查接入”核实机器人身份。开发机需要能主动访问飞书，无需公网事件回调地址。然后在飞书开放平台“事件与回调”选择长连接方式，订阅 `im.message.receive_v1`，申请 `im:message.group_at_msg:readonly` 和发送消息权限，按提示发布应用并将机器人加入群。平台账号列表显示连接状态和错误；后台进程关闭或长连接断开可能丢失超过飞书重试范围的事件。仅申请 @ 权限时，不支持通过手动或定时历史同步补拉群消息，请在渠道将定时同步设为 0。长连接支持消息、撤回和卡片操作回调；使用卡片时还需订阅 `card.action.trigger`。网页登录回调仍需在应用安全设置中登记，并由用户浏览器访问。

平台 API 地址和账号状态位于“高级设置”；API 地址留空使用所选平台的默认地址。编辑时密钥输入框留空会保留已保存的密钥。

账号已保存不代表接入成功。“检查接入”会核实基础 API 访问及已配置渠道的可读范围，不表示外部群、普通消息或全部历史权限已经具备。点击“查看检查结果”可按能力查看结果、原因和适用渠道；只读检查与实际收到消息、发送成功的记录分别展示。当前渠道与平台账号配置下没有发送成功记录时，回复不能直接使用自动审批规则，首次须由人工审批后调用平台验证。界面检查结果与真实租户验收应一起检查。个人身份绑定不扩大连接器可读取的会话、文档或消息范围。

- 问题详情保留附件引用与未解析说明。授权成员可按需下载支持的图片、PDF 或文本/日志，单项上限 4 MiB；下载时重新核对问题版本、来源消息和渠道权限。图片附件不会统一归档，但当前问题中的授权图片可在回答/分类时按需抓取，单张上限 2 MiB、最多 3 张，仅以内存中的 base64 data URL 形式送入模型；未知格式、HTML、SVG、压缩包和可执行文件拒绝下载或入模。

飞书 / Lark 群渠道可在“消息渠道”中设置“定时同步间隔”：0 关闭，1–1440 分钟开启，默认关闭。定时同步复用手动历史同步：首次从已完成的手动同步进度继续；没有可靠进度时读取机器人可访问的历史消息，后续按上次定时同步成功的进度增量读取，并重叠 5 分钟去重。分页和话题均完成后才推进定时进度；失败会重试并在渠道显示错误。历史消息按手动同步处理，不会自动发送回复。需要机器人已加入群并有读取历史消息的权限；服务无法访问飞书、权限不足或消息不可见时无法完成同步。账号身份或群变更后需要重新开启定时同步。

## 3. GitHub

接收和回复 Issue 反馈：

1. 在“设置 → 平台账号”的“GitHub Issue 反馈”入口点击“添加 GitHub 账号”，填写账号名称。
2. 手动填写 GitHub 所有者（Owner）、仓库名和访问令牌（Token）；也可选择已启用的“已有代码仓库”，复用其仓库地址。该平台账号没有保存独立 Token 时，会使用所选代码仓库的 Token；编辑时输入框留空会保留已有 Token。
3. 可选配置 Webhook：签名密钥与 GitHub 仓库 Webhook 的 Secret 保持一致，回调地址为 `PUBLIC_URL/hooks/github/{connector_id}/events`，需要 GitHub 能访问的 HTTPS 入口。没有公网入口时可以使用下述定时轮询。
4. 保存后点击“检查接入”，再到“设置 → 消息渠道”选择该 GitHub 账号，填写接收范围和回复方式。保存账号不代表仓库权限或 Webhook 已验收，应查看检查结果并验证实际事件。

消息渠道的接收范围对应 `external_id`：

| 填写内容 | 接收内容 |
|---|---|
| `issue:123` | 编号 123 的 Issue 事件及普通评论；PR 的普通评论也使用 `issue:N` |
| `pull:123` | 编号 123 的 PR 状态事件；接收该 PR 的普通评论还需配置 `issue:123` |
| `owner/repo` | 该仓库的 Issue、普通评论和 PR 状态事件 |

平台 API 地址、账号状态和可选的“GitHub 评论发送账号”位于“高级设置”。检查 PAT 时若能读取当前账号，会自动记录发送者身份；其他令牌可填写评论发送账号，例如应用机器人的 `sender_login`。发送结果不明确且无法核对评论作者时，仅有相同关联标记不能证明评论已发送成功。

GitHub Issue 渠道可设置“定时同步间隔”：0 关闭，1–1440 分钟开启；默认为关闭。首次开启或重新启用渠道从当前时间开始，不自动导入所有历史 Issue。之后按上次成功时间增量查询，并向前重叠最多 5 分钟以降低时间边界漏读，重复事件会去重。轮询处理新 Issue、新增或修改的普通评论，以及已收录 Issue 的正文更新；需要旧 Issue 上下文时先在渠道点击“同步”导入历史。轮询当前不接收 PR 状态变化、删除事件或未收录的旧 Issue 正文更新。GitHub 返回错误时不推进轮询进度，后台任务会重试，最终失败原因显示在渠道和后台任务中。渠道或关联仓库配置改变时，旧任务不会覆盖新配置；关联仓库身份改变后需要关闭再重新开启轮询。

轮询到的新内容按渠道的回复方式和回复审批规则处理；手动历史同步仍只生成草稿或转人工，不自动发送。轮询依赖开发机主动访问 GitHub API、有效令牌及相应读取权限；请求可能受 GitHub 限流和网络稳定性影响。机器人账号自己的评论会被忽略以防止循环回复。

开发和提交 PR 在“设置 → 代码仓库”中配置：填写 owner/repo、起始分支、允许修改的路径、固定 digest 的任务运行镜像、可信测试命令参数和 Token。按实际用途授予代码读取/写入、PR 创建及检查结果读取权限。仅需要开发和提交 PR 时，直接配置代码仓库即可，无需添加用于接收 Issue 的 GitHub 平台账号；接收 Issue 也可直接手填仓库，无需先配置开发任务的运行镜像和测试命令。

首次发布创建 `agentowl/{task_id}` 分支和 Draft PR。Git 对象、分支与 PR 写入全部由 Worker 执行，发布前再次检查审批、代码摘要和目标分支。后续修订基于已确认的任务分支；更新要求当前 HEAD 匹配冻结证据，并使用非强制更新。审查或 CI 反馈不会绕过开发者确认和审批。

PR 合并后，开发任务完成，问题进入等待发布/用户验证；合并不等于版本已发布，也不等于用户问题已解决。自动合并和生产发布不在此流程内。

## 4. 知识与 Oncall

- 在“设置 → 知识来源”中关联仓库 Markdown、飞书 docx 文档或人工整理内容；同步正文产生草稿。文档内容变化、来源权限失效或来源范围修改会撤下旧知识，并使相关待发审批失效。
- 知识发布前由具备权限的成员审核。外部渠道只能使用公开知识。来源权限检查超过 24 小时的知识不能用于回复，定时同步会重新检查。
- 适用版本使用完整 SemVer，支持 `>`、`>=`、`<`、`<=`，空格或逗号分隔的条件按 AND 匹配。环境使用 `/` 分隔 OS、部署环境和认证方式；案例缺少知识要求的版本或环境条件时，不使用该知识回答。
- 已发送且人工确认的回复可在问题详情点击“保存为知识草稿”，整理适用版本、环境和排查步骤后提交发布审批。历史原话不会直接变成公开事实。
- 在“设置 → 值班安排”中配置模块负责人、备用负责人和通知渠道。模型没有充分依据、未配置模型或达到预算时转人工。超时提醒按问题版本和时间窗口去重。
- “接管并暂停自动回复”暂停自动回复；恢复前确认当前渠道策略。用户消息编辑或撤回会使依赖旧上下文的待发动作失效。

问题详情提供“已解决／未解决／转人工”反馈。Lark 答复卡片提供相同按钮；GitHub 答复附带可复制的反馈评论命令。平台反馈只接受原问题参与者，绑定本条答复、渠道、来源消息与当前版本；旧答复、撤回后的消息或其他群转来的按钮不能改变问题。反馈不具有开发或审批权限。“转人工”暂停自动回复，“未解决”回到继续排查并通知负责人。

## 5. 模型与任务执行

### 5.1 网页配置

在“设置 → 模型接口”填写 API 地址、模型名称、密钥和每日 Token 上限，按服务能力选择 JSON 输出格式与 Token 参数，再启用模型。API 地址填写 `/chat/completions` 前的路径，例如 `https://api.example.com/v1`；HTTP 地址需要明确开启“允许 HTTP”，仅用于可信开发环境。配置保存在 PostgreSQL，密钥加密保存。密钥输入框留空保留已有值，勾选“清除已有密钥”才会删除；更换 API 地址时须重新填写密钥或明确清除。保存不会测试模型连接。

在“设置 → 任务执行”配置开发审批、容器环境和执行额度。页面同时展示执行器连接、隔离检查、宿主配额能力和配置版本；未取得能力时显示待验证，配置已保存不代表执行器已经可以运行。新部署通过 `make init` 生成固定机器 ID，API 首次创建管理员时自动登记“本机”，页面聚合展示机器池状态。已有部署和机器配置不自动修改。

| 配置项 | 使用方式 |
|---|---|
| 开发审批 | 在“审批策略”中配置。每种操作分别配置人工、自动或禁止；未匹配时人工审批 |
| 任务网络 | 默认不联网。选择 Docker bridge 后，任务可访问专用 Rootless 网络能到达的地址，不提供域名白名单；允许联网不保证外网连通，需检查宿主路由 |
| 根文件系统只读 | 默认开启。关闭后可写入容器内当前用户有权限的目录，容器删除后不保留；任务仍为非 root 用户，安装系统软件包可能需要预先构建镜像 |
| 测试工作目录 | 默认只读。允许写入后，在本次执行专属的匿名 Docker 卷内使用 `/workspace/source` 临时副本安装项目依赖和生成构建文件，新增文件不进入代码产物或 PR；修改、删除已有源码或锁文件，或改变其类型／执行权限，会使测试失败。整个卷受专用运行盘总容量约束，执行结束后删除 |
| 执行时限 | 填 `1–3600` 秒时超时停止，填 `0` 表示不设执行超时；暂停、审批失效或运行许可撤销仍会停止任务 |
| 运行与资源 | 配置 CPU／内存／进程配额和并发；内存使用 MiB，CPU 使用毫核，`1000` 毫核为 1 核 |
| 文件与模型用量 | 代码快照、代码文件数、产物、工具调用次数和模型 Token 五项默认 `0`，表示不设单次任务额度；可填写正整数自行限制。代码快照与产物使用 MiB。测试新增依赖和构建文件不计入代码快照与代码文件数额度；实际可处理量仍取决于宿主可用磁盘、内存和模型服务能力，每日 Token 总额度独立生效；单次任务 Token 为 `0` 时会预留当日剩余额度，结束后按实际用量结算，期间其他模型调用可能等待 |
| 重试策略 | 普通后台任务可配置最大尝试次数、初始间隔和最大间隔，失败后按指数退避；模型分类、回复生成、同步、通知入队等任务使用这组配置。平台写入（发送回复、Oncall 通知）默认不自动重发，只核对不明确结果；如显式开启平台写入自动重试，仅对临时错误或不明确结果重试，明确权限/参数错误仍直接失败。 |


“设置 → Runtime Machines”用于登记执行宿主。每条记录至少包含执行地址、回调地址、调度权重、状态和镜像白名单，以及执行访问令牌与回调令牌。系统从 `active` / `degraded` 且就绪的机器中选择执行宿主；`draining` 机器只排空，不接收新的 attempt；`disabled` 机器完全跳过。选择结果冻结到 `run_attempts.runtime_machine_id`，一旦某个 attempt 被某台机器接受，后续只会向这台机器轮询、收集产物与停止，不会静默迁移到其他机器。

已登录成员均可查看这两页，只有管理员可保存。每次保存分别递增模型或执行配置版本，后续执行读取新配置，无需重启服务。旧的待执行步骤审批会失效，相关任务进入无法继续状态；在开发任务页面恢复后，按新配置重新审批。运行中的尝试保留原模型、网络、文件系统权限和额度，不在中途切换。

### 5.2 Runtime Machine 宿主初始化

Runner Controller 是 Runtime Machine 的实现之一，Web 中的“开发任务”是它的控制界面。启用实际执行要求专用 Linux 宿主环境：systemd、rootless Docker、uidmap、e2fsprogs 和 Python。默认资源模式 `required` 还要求 cgroup v2 及可用的 CPU、内存和 PID 限制。

```sh
sudo script/runner-setup.sh \
  --data-root /项目绝对路径/deploy/data/runner \
  --resource-limits required
```

脚本创建专用账号、独立 rootless daemon、有预分配容量边界的 runtime 文件系统和有字节/inode 上限的工作区。它会修改宿主账号、systemd 与挂载配置；上线人员应先审阅脚本，在目标宿主显式执行。不会复用应用服务的 Docker daemon。

资源模式在“设置 → 任务执行”保存，只接受 `required` 或 `disabled`，默认 `required`。仅可信开发环境可显式使用 `disabled`，例如未提供 cgroup v2 的开发机。该模式不提供 CPU、内存和 PID 硬上限，任务可能耗尽宿主资源，同时执行的任务数必须为 1。使用此模式时，初始化与预检命令都传入 `--resource-limits disabled`；脚本参数只选择宿主检查范围，不修改网页配置。其他宿主和隔离要求仍须通过预检。

将输出的 UID/GID、`RUNNER_HOST_DATA_ROOT` 写入 `deploy/.env`。在该专用 daemon 中预装并核验工具链镜像，填写 `RUNNER_ALLOWED_IMAGES` 和仓库 `runner_image`，两者都使用完整 `image@sha256:...`。镜像需提供 `/bin/sleep`，宿主预检还会用到镜像内的 `/bin/sh` 和 `cat`；执行用户为容器内 65532。专用 socket 位于权限受限的 `control` 目录，预检由 root 或专用 Runner 账号执行。

仓库实际测试还需要镜像提供对应语言、构建工具和依赖；基础 Alpine 镜像只能用于容器隔离冒烟，不能代替业务工具链镜像。

所有任务都在独立容器中使用非 root 用户，容器不挂载 Docker Socket 或模型密钥，持续检查运行许可。网络、根文件系统、测试目录写入和时限使用网页配置；`required` 模式另限制 CPU、内存和 PID。离线执行时依赖应预先放入镜像或缓存；联网并允许测试目录写入时可在临时副本中准备项目依赖。Go 项目可通过代码仓库的“运行配置（JSON）”指定缓存位置，下面是离线缓存示例：

```json
{"test_env":{"GOMODCACHE":"/opt/go/pkg/mod","GOCACHE":"/output/go-cache","GOPROXY":"off","GOSUMDB":"off"}}
```

仅允许工具链和缓存相关环境变量，不接受测试凭据或任意宿主挂载。`test_argv` 每一项是独立参数，不经过 Shell；例如 `go`、`test`、`./internal/auth/...`。使用自定义脚本时仍在隔离容器内运行，且脚本本身属于审批快照。

```sh
sudo script/runner-preflight.sh \
  --data-root /项目绝对路径/deploy/data/runner \
  --resource-limits required \
  --image '工具链镜像@sha256:实际摘要'
```

预检模式应与网页选择的资源模式一致。新部署的“本机”已自动关联 `RUNNER_MACHINE_ID`、内部执行/回调地址及初始化生成的两个令牌；重复启动不会覆盖管理员修改或恢复已删除的记录。自动登记不负责宿主初始化，也不会自动启用 Runner。完成上述初始化与预检后，启用 runner profile。已有部署或额外机器仍需在“设置 → Runtime Machines”登记，并将对应记录 ID 写入 `RUNNER_MACHINE_ID`：

```sh
docker compose --env-file deploy/.env -f deploy/compose.yaml --profile runner up -d --build
```

每台 Runtime Machine 都需要各自的执行地址、回调地址、访问令牌、回调令牌、镜像白名单与宿主磁盘配置。执行地址用于 `Start/Inspect/Stop/Collect/Acknowledge`，回调地址用于读取 settings、context manifest/ref 与运行许可。Runner 回调必须携带机器自身的 `machine_id` 和 `callback_token`。模型、开发审批、容器运行选项和执行额度统一在网页保存。执行器每次接收新任务都会重新读取配置，并核对审批绑定的版本。宿主检查不通过或模型未就绪时，页面显示原因并阻止新执行。

运行许可每次启动和持续执行都向 API 内部端口核验。暂停、撤销、权限/仓库配置变化或许可过期会停止执行。测试源代码变化、归档路径异常、摘要不匹配、缺失测试证据均不能发布。产物按已保存的任务额度和宿主实际可用空间处理；填 `0` 不设任务产物额度，磁盘空间不足时仍会停止写入。有引用的证据不会被孤儿清理任务删除。

## 6. 审批、失败与核对

任务可由开发者在问题详情确认，也可由“创建开发任务”策略生成建议后进入统一审批列表。审批策略覆盖创建、回复、知识发布和各开发步骤。禁止优先于人工、人工优先于自动；多个自动规则按更严格的额度执行。生成方案、修改代码、运行测试、审查变更和提交 PR 分别按各自策略审批；未匹配策略时人工审批。审批条件、来源或授权变化会阻止旧批准执行；信息不全的任务建议显示“需补充信息”，可回到问题补充后重新生成。提交 PR 仍须通过当前快照的测试。

审批通知默认开启，覆盖人工待审批、自动批准、策略禁止，以及人工通过、拒绝、撤销；任务建议信息不全时也会通知。每条策略可独立关闭通知，并指定启用的内部渠道；未指定时使用问题模块对应的值班通知渠道，没有模块的知识发布使用 `*` 路由。未匹配策略的审批默认通知。修改通知开关或渠道不会使已有审批或任务授权失效。没有可用渠道时，审批照常保存，后台通知任务记录失败；发送失败或结果未知可在后台任务和外部操作中查看。关闭开关会拦截尚未发送的通知，已发出或发送中的消息无法撤回。历史审批不补发。

审批策略按操作类型显示和保存可生效的字段：发送回复只按渠道范围匹配，不使用仓库或代码路径；知识发布不使用渠道、仓库、路径或测试通过条件；开发步骤才使用仓库、路径和测试条件。保存策略会清理当前操作类型无效的旧字段，避免因为隐藏范围残留导致策略无法命中。回复自动审批还要求该渠道当前账号配置已有一次成功发送或通知记录。


审批展示冻结的方案、路径、命令、自测和产物。恢复失败任务、修改目标或继续修改 PR 时会产生新的执行版本，旧审批不能复用。

“后台任务”可查看失败原因并重新处理已失败任务。管理员可忽略单条或当前页失败任务；已忽略任务仍保留在“已忽略”筛选中，可恢复提醒或重试。忽略只影响概览计数，不改变实际失败状态，重试后再次失败会重新显示。重试保留原业务去重键；它不会绕过暂停、过期审批或外部写入状态机。过时的开发任务请从开发任务页面恢复或修改目标。

Oncall 通知入队后会创建平台操作；发送失败或结果不明确时，会在对应问题的操作记录中写入“Oncall 通知发送失败”或“Oncall 通知结果待核对”，并在操作记录中保留平台错误。

外部写入超时可能已经生效。此时状态为 `outcome_unknown`，系统只查询核对，不直接重发。GitHub 通过任务分支、PR/评论关联标记及发送者身份核对；Lark 已有 message_id 可查，只有 UUID 且没有远端 ID 的不确定发送可能无法自动确认，需要平台侧人工查证。撤销不能撤回已经在远端生效的请求。

“操作记录”列表在每条记录标题前显示来源／状态标识，便于区分用户反馈、操作、审批、自动审批和平台操作。问题详情的操作记录与首页最近动态使用同一套标识；平台操作仍同时显示执行状态，`outcome_unknown` 需要按上段流程核对。


日志不得记录密钥、完整 Token 或原始上游错误体。错误页面保留请求 ID；支持日志和产物经过脱敏，但源码本身仍是受访问控制的数据。

## 7. 备份与迁移

业务数据库、加密主密钥和产物必须一起保留。丢失 `encryption_key` 将无法解密连接器凭据。备份包包含 Secret，须限制权限并放在受控存储。

当前脚本采用 Linux 冷备份：

1. 在 Web 停止接收新任务，暂停并确认运行已终止。
2. 若启用了 Runner，先由宿主管理员停止专用 daemon，卸载其 `runtime` 和 `tasks`。脚本会验证已停止，不代为修改宿主 systemd。
3. 执行 `sudo script/backup.sh --output /受控目录/agentowl-backup.tar`。脚本停止 Compose 服务，校验停机后复制数据和配置，生成 SHA-256，保留数字 UID/GID。
4. 目标主机准备相同项目版本和空的 `deploy/data`；先准备原部署 UID/GID，若含 Runner，还须创建原 Runner UID/GID 及相同 subuid/subgid 映射，并选择兼容的 Docker/storage driver。将归档和相邻的 `.sha256` 文件一起复制，再执行 `sudo script/restore.sh --archive /受控目录/agentowl-backup.tar`。脚本在恢复前校验摘要、路径、类型、配置、账号映射与剩余空间。
5. 按目标绝对路径调整 Runner 账号 home、`deploy/.env` 中的 `RUNNER_HOST_DATA_ROOT`，重新运行宿主初始化并预检。旧 socket、tmpfs 工作区不作为持久状态迁移。若迁移后用于 `make dev`，同时修正 `deploy/data/secrets/dev.env` 中的旧绝对路径；Compose 不读取这个开发配置文件。
6. 核对域名、身份源和路径后运行 `make migrate`、`make up`，验证登录、问题/知识、审批和产物读取，再恢复接入。需要恢复 Runner 时使用第 5 节带 `--profile runner` 的启动命令；`make up` 默认不启用 Runner。

备份/恢复结束后服务保持停止，便于检查。运行中的数据库目录直接拷贝不能保证一致性；停止任务也不等于可以省略数据库停机。
