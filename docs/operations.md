# AgentOwl 运维手册

## 1. 部署与身份配置

AgentOwl 面向单团队、单主机部署。Compose 中所有持久化数据都挂载在同级 `./data` 目录下，HTTPS 与反向代理交由宿主机 Nginx 处理。

### 首次启动步骤

1. 用普通部署账号运行 `make init`，确认 `deploy/.env` 中的 `APP_UID` / `APP_GID` 与目录属主一致。
2. 生产环境在 `deploy/.env` 中配置 `PUBLIC_URL=https://你的域名`、`AUTH_MODE=oidc`、`OIDC_ISSUER`、`OIDC_CLIENT_ID`、`BOOTSTRAP_EMAIL` 和 `BOOTSTRAP_SUBJECT`。身份源的回调地址填 `PUBLIC_URL/auth/callback`。
3. 将客户端密钥写入 `deploy/data/secrets/oidc_client_secret`。首个管理员必须通过 `BOOTSTRAP_SUBJECT` 指定稳定的 OIDC Subject（不会仅凭邮箱自动授予管理员权限）；其余成员上线后由管理员在「设置 → 团队成员」添加。
4. 执行 `make up`，依次确认一次性迁移完成、本机 `http://127.0.0.1:8080/health/ready` 返回正常，以及 Web 登录页可打开（健康检查直接请求 API，不走前端代理）。
5. 参考 `deploy/nginx.example.conf` 配置域名与 TLS。Web 和 API 默认映射宿主机回环地址的 `3000` / `8080` 端口；若改动 `WEB_PORT` / `API_PORT`，记得同步更新 Nginx 上游地址。内部许可端口 `8081`、Runner 端口 `8090` 与数据库均不应对公网开放，Nginx 必须拦截对 `/internal/` 的外部访问。

### 登录与权限说明

- 本地密码登录仅建议用于开发或内部受控环境，密码长度要求至少 12 字节。
- 会话 Cookie 开启 `HttpOnly`、`SameSite=Lax`（HTTPS 下开启 `Secure`），所有写接口均校验 CSRF Token。停用成员或修改授权后，其现有会话会立即失效。
- 内置角色包括 `admin`、`developer`、`oncall`、`knowledge`、`viewer`，单个成员可拥有多个角色。渠道与仓库授权按系统 ID 配置，`*` 表示允许访问全部资源。在飞书卡片中点击按钮不会自动获得 Web 权限。

## 2. 飞书 / Lark 接入

### 2.1 创建平台账号与消息渠道

进入「设置 → 平台账号」，点击 **+ 飞书 / Lark** 填写配置：

1. 选择平台（飞书或 Lark 国际版），填写账号名称、App ID、Tenant ID 和 App Secret。
2. 决定事件接收方式：
   - **HTTP 回调**（需要公网 HTTPS）：在飞书开放平台开启 v2 事件推送，回调地址填 `PUBLIC_URL/hooks/{provider}/{connector_id}/events`；将平台提供的 Verification Token 和 Encrypt Key 填入账号配置。卡片按钮回调可直接复用 `/events`，如平台允许单独设置，也可填 `PUBLIC_URL/hooks/{provider}/{connector_id}/actions`。
   - **长连接**（无需公网回调）：开启「启用长连接」，在飞书开放平台「事件与回调」中选择长连接模式，订阅 `im.message.receive_v1`（使用卡片时一并订阅 `card.action.trigger`），并申请 `im:message.group_at_msg:readonly` 与发消息权限。长连接要求部署机能主动访问飞书；若进程停止或断连超过飞书重试窗口，期间事件可能丢失。
   - 仅使用手动/定时历史同步时，无需填写 Verification Token 和 Encrypt Key。
3. 保存后点击「检查接入」核实基础连通性。
4. 进入「设置 → 消息渠道」，关联该平台账号并填写群 `chat_id`（`oc_...`）。未登记或已停用的群不会采集消息；私聊消息（P2P）会自动归入虚拟私聊会话并可直接回复，不会在消息渠道列表中生成多余条目。
5. 建议新接入的群先设为「仅生成草稿」，观察回复质量后再开启自动回复策略。

> 平台 API 地址和账号状态收纳在表单底部的「高级设置」中，API 地址留空即使用官方默认值。编辑账号时，所有密钥字段留空都会保留原有值。

### 2.2 飞书登录与身份绑定

已有成员绑定飞书账号后，既可直接用飞书登录 Web，也能在审批卡片、任务上下文中自动识别同一成员身份：

1. 在飞书/Lark 应用的安全设置中登记回调地址 `PUBLIC_URL/auth/lark/callback`（也可在「个人中心 → 飞书账号 → 应用配置」直接复制），发布应用并把团队成员加入可用范围。
2. 在「设置 → 平台账号」打开该应用的「飞书登录与绑定」开关。
3. 成员用现有账号登录 AgentOwl，在「个人中心」选择应用并完成飞书授权。管理员也可在「设置 → 身份绑定」手动维护成员与 Open ID 的对应关系。

身份绑定遵循以下规则：
- 严格按 `(provider, app_id, open_id)` 精确匹配，不按姓名或邮箱自动合并账号，也不会创建新成员或改变原有角色与资源范围。
- 同一成员在同一个应用下只能绑定一个飞书账号；更换绑定需先解绑。解绑会立即撤销该绑定对应的登录会话，成员唯一可用的登录方式不允许自行解绑。
- 授权拿到的用户 Token 仅用于读取本人身份，不会落库、续期或传给模型；收发消息、读文档和发通知仍使用应用自身身份与权限。

### 2.3 能力检查、定时同步与附件限制

- **检查接入与实测区分**：点击「检查接入」只会探测机器人基础 API 和已配置渠道的只读权限，不代表已拿到外部群、普通群消息或完整历史权限。点「检查结果」可以逐项查看原因和适用渠道。在某渠道与当前账号配置下尚未成功发送过消息前，回复策略不能走自动批准，首次发送必须经人工审批完成验证。
- **定时历史同步**：在「消息渠道」中可为飞书/Lark 群设置定时同步间隔（`0` 关闭，`1–1440` 分钟开启，默认关闭）。定时同步复用手动同步逻辑：首次从上次完成的手动进度继续（无进度则拉取可见历史），后续按上次成功时间增量拉取并向前重叠 5 分钟去重；分页和话题全部拉完才推进进度。如果应用只申请了 `@` 消息权限而无群历史读取权限，请将同步间隔保持为 `0`。定时同步拉来的历史消息不会自动触发回复。
- **附件读取与图片入模**：问题详情默认保留附件引用，授权成员可按需下载图片、PDF 和文本/日志（单文件上限 4 MiB），下载时会重新校验问题版本和渠道权限。图片不会落盘归档，在分类和答复时由后端按需抓取（单张上限 2 MiB、每次最多 3 张），仅在内存中转为 base64 传给模型；HTML、SVG、压缩包、可执行文件及未知类型一律拒绝下载和入模。

## 3. GitHub 接入

### 3.1 接收与回复 Issue 反馈

1. 在「设置 → 平台账号」点击 **+ GitHub**，填写账号名称。
2. 选择「关联已有代码仓库」（不单独填 Token 时会自动复用该仓库的访问凭据），或手动填写仓库所有者、仓库名与 Token。
3. 如部署机有公网 HTTPS 入口，可配置 Webhook：在 GitHub 仓库填写回调地址 `PUBLIC_URL/hooks/github/{connector_id}/events`，并将相同 Secret 填入账号的「Webhook 签名密钥」。没有公网入口时可改用下文的定时轮询。
4. 保存并点击「检查接入」，再到「设置 → 消息渠道」关联该账号，设置接收范围和回复方式。

消息渠道中「Issue / PR 或仓库范围」的填写格式如下：

| 填写内容 | 监听范围 |
|---|---|
| `issue:123` | 指定 Issue 的事件与普通评论（如需监听某个 PR 的普通评论，同样填 `issue:编号`） |
| `pull:123` | 指定 PR 的状态变化事件 |
| `owner/repo` | 整个仓库的 Issue、普通评论与 PR 状态事件 |

> 「高级设置」中可填写可选的「评论发送账号」。使用 PAT 时点击检查接入会自动识别当前账号；使用 GitHub App 等其他令牌时，建议填入机器人的 `sender_login`，用于在结果不明确时核对评论归属。

### 3.2 GitHub 定时轮询

无公网 Webhook 时，可在 GitHub 消息渠道设置「定时同步间隔」（`0` 关闭，`1–1440` 分钟开启，默认关闭）：

- 首次开启或重新启用时从当前时刻起增量查询，不会一口气拉取全部旧 Issue；需要旧 Issue 上下文时可先手动点一次「同步」。
- 每次轮询按上次成功时间向前重叠最多 5 分钟，避免边界漏读并自动去重；覆盖新 Issue、新增/编辑的普通评论，以及已收录 Issue 的正文更新（暂不包含 PR 状态变化、删除事件或未收录旧 Issue 的正文更新）。
- 轮询拉到的新内容会正常按渠道回复方式和审批策略处理；手动同步只生成草稿或转人工，不会自动回复。机器人的评论会自动忽略以防循环触发。
- 若 API 报错，同步游标不会推进，后台任务会按重试策略重试并在界面展示错误。更换渠道关联的仓库后，需先关闭再重新开启轮询。

### 3.3 代码仓库与 PR 发布

如果只需要自动开发和提 PR，直接在「设置 → 代码仓库」配置即可，不必先建用于收 Issue 的平台账号；反之亦然。

代码仓库需配置 `owner/repo`、起始分支、允许修改的路径、带 `@sha256:...` 摘要的任务运行镜像、测试命令参数和访问 Token（按需授予代码读写、PR 创建及 Check 读取权限）。

- 首次发布由 Worker 创建 `agentowl/{task_id}` 分支和 Draft PR，发布前再次校验审批记录、代码快照摘要和目标分支。
- 收到 Review 或 CI 反馈后，后续修改仍需经过确认和审批流程，并基于同一任务分支以非强制推送方式更新原 PR（更新前检查远端 HEAD 与当前证据一致）。
- PR 合并后开发任务结束，对应问题转入「待发布」等待发版与用户验证——PR 合并既不等于线上已发版，也不等于用户问题已解决。

## 4. 知识库与值班

- **知识来源**：在「设置 → 知识来源」关联仓库 Markdown、飞书 docx / Wiki 文档或人工录入来源。同步后生成草稿，经具备 `knowledge` 权限的成员审批后发布。一旦源文档变更、权限失效或范围收窄，旧知识会被下架且关联的待发审批自动失效。
- **权限与生效条件**：外部渠道只能检索「公开」知识；来源权限超过 24 小时未复检的知识不会参与自动回复（定时同步会自动续检）。适用 CLI 版本采用完整 SemVer 表达式（支持 `>`、`>=`、`<`、`<=`，多条件用空格或逗号分隔取交集），环境字段按 `/` 分隔 OS、部署环境和认证方式；当问题缺少知识所要求的版本或环境信息时，不会强行套用。
- **问答转知识**：对于已发送并确认有效的回复，可在问题详情页点「保存为知识草稿」，补充适用条件与步骤后走发布审批，避免把未经整理的聊天原话直接当成公开文档。
- **值班与人工接管**：在「设置 → 值班安排」按模块设置主负责人、备用负责人、通知渠道和响应时限。模型未配置、证据不足或触及每日额度时自动转人工。处理人可随时点击「接管并暂停自动回复」介入，恢复自动回复需手动操作；当原消息被编辑或撤回时，基于旧内容生成的待发草稿会自动失效。
- **用户反馈**：问题详情页、飞书答复卡片和 GitHub 回复命令均支持「已解决 / 未解决 / 转人工」。平台侧反馈仅接受原问题参与者，且严格绑定当条答复、渠道和版本，转发卡片或旧答复按钮不会生效；反馈操作也不附带任何开发或审批权限。

## 5. 模型与任务执行

### 5.1 网页配置

模型接入与运行约束均保存在 PostgreSQL，所有登录成员可查看状态，仅管理员可修改。每次保存都会递增对应配置版本号，无需重启服务；尚未执行的旧步骤审批会自动失效（任务在开发详情页恢复后重新审批），已在跑的任务继续沿用启动时的配置快照。

- **模型接口**（`设置 → 模型接口`）：填写 `/chat/completions` 上一级的根地址（如 `https://api.example.com/v1`）、模型名称、API 密钥、每日 Token 上限，按供应商特性选择 JSON 格式和 Token 参数名后开启即可。HTTP 地址仅限内部调试，需勾选「允许 HTTP 地址」。密钥加密存储且不回显，留空保留原值，更换地址时需重新填写或勾选「清除已有密钥」。保存操作本身不会主动请求模型接口。
- **任务执行**（`设置 → 任务执行`）：配置沙箱运行环境、资源限制、用量上限与重试策略，顶部实时展示各运行机器的连通性、隔离检查与就绪状态。

| 配置项 | 说明 |
|---|---|
| 审批策略 | 在「设置 → 审批策略」统一管理。按操作类型设置人工、自动或禁止；未命中任何策略时走人工审批 |
| 任务网络 | 默认断网。选「允许联网」后接入专用 Rootless Docker 的 bridge 网络，不设域名白名单，实际连通性取决于宿主机路由 |
| 根文件系统只读 | 默认开启。关闭后允许写入容器内当前用户有权限的目录，容器销毁即清空；容器内始终为非 root 用户 |
| 允许测试写入临时目录 | 默认关闭（只读）。开启后在本次执行专属的匿名 Docker 卷里复制出 `/workspace/source` 运行测试，可安装依赖，新增文件不进 PR；若修改/删除已有源码或锁文件，测试直接判定失败 |
| 单次最长运行时间 | `1–3600` 秒按时限超时终止；填 `0` 不限时，但暂停、审批失效或运行许可被撤销仍会立刻停止任务 |
| 运行限制 | 配置并发数、内存（MiB）、CPU（毫核，1000 毫核 = 1 核）与进程数（PID）上限 |
| 用量上限（0 为不限） | 代码快照、文件数、产物大小、工具调用次数和单次模型 Token 默认均为 `0`（不设单次上限），可按需填正整数。测试新增依赖不计入快照和文件数。单次模型 Token 为 `0` 时，执行前会预占当日剩余总额度、结束后按实际消耗结算，期间其他并发模型调用可能短暂等待 |
| 重试策略 | 后台任务（分类、草稿、同步、通知入队等）按最大次数与指数退避重试。平台发送（回复、值班通知）默认不自动重试，仅在结果不明时核对；显式开启重试后也只针对临时错误或不确定结果，权限/参数错误直接失败 |

- **运行机器**（`设置 → 运行机器`）：管理可接入的执行宿主。首次部署时，`make init` 会生成固定机器 ID，API 初始化管理员时会自动登记一台「本机」记录（不会覆盖管理员后续修改）。每台机器需配置执行地址、回调地址、调度权重、状态（`active` / `degraded` / `draining` / `disabled`）、镜像白名单及双向访问令牌。
  - 系统仅从 `active` 或 `degraded` 且已就绪的机器中按权重选机；`draining` 仅排空在跑任务，不接新任务；`disabled` 完全跳过。
  - 选机结果会绑定到 `run_attempts.runtime_machine_id`，一旦机器接单，后续轮询、取产物和停止指令只发给该机器，不会中途迁移。

### 5.2 运行机器宿主初始化

实际执行仓库开发任务需要准备一台 Linux 宿主机，预装 `systemd`、`rootless Docker`、`uidmap`、`e2fsprogs` 和 Python。生产默认的 `required` 资源模式还要求宿主机启用 cgroup v2 及 CPU、内存、PID 控制器。

#### 1. 初始化专用账号与隔离环境

```sh
sudo script/runner-setup.sh \
  --data-root /项目绝对路径/deploy/data/runner \
  --resource-limits required
```

该脚本会创建独立的低权限 Runner 账号、专用 Rootless Docker daemon、固定容量的 runtime 文件系统，以及限制容量和 inode 的任务工作区（完全独立于宿主机主 Docker）。由于涉及系统账号、systemd 和挂载点变更，上线前请先审阅脚本再执行。

> 如果宿主机暂不支持 cgroup v2（例如老内核的内部开发机），可将脚本与预检参数改为 `--resource-limits disabled`，并在「设置 → 任务执行」同步选择关闭资源限制（并发将强制锁死为 1）。请注意，该模式下任务没有 CPU、内存和 PID 硬上限，仅限内部开发环境使用。

#### 2. 配置环境变量与工具链镜像

将初始化脚本输出的 UID/GID 和 `RUNNER_HOST_DATA_ROOT` 写入 `deploy/.env`。在刚建好的专用 Docker daemon 中拉取并核验业务所需的工具链镜像，将带完整 `@sha256:...` 摘要的镜像地址填入 `RUNNER_ALLOWED_IMAGES` 和代码仓库的「任务运行镜像」。

- 镜像内需包含 `/bin/sleep`（宿主预检另需 `/bin/sh` 和 `cat`），容器以 UID `65532` 运行。
- 基础 Alpine 镜像只适合做环境连通性自检，业务项目需要打包对应的语言编译器与构建工具。离线运行时需预装依赖或缓存，Go 项目可在仓库「运行配置（JSON）」中指定缓存路径：

```json
{"test_env":{"GOMODCACHE":"/opt/go/pkg/mod","GOCACHE":"/output/go-cache","GOPROXY":"off","GOSUMDB":"off"}}
```

> 「运行配置（JSON）」只允许填写工具链和缓存类环境变量，不支持传入凭据或宿主挂载。仓库的 `test_argv` 按行拆分为独立参数直接 exec，不经 Shell 解析。

#### 3. 执行宿主预检并启动 Runner

```sh
sudo script/runner-preflight.sh \
  --data-root /项目绝对路径/deploy/data/runner \
  --resource-limits required \
  --image '工具链镜像@sha256:实际摘要'
```

确认预检通过（参数需与网页端选择的资源模式一致）后，检查 `deploy/.env` 中的 `RUNNER_MACHINE_ID` 与「设置 → 运行机器」中的记录 ID 一致，再以 `--profile runner` 启动：

```sh
docker compose --env-file deploy/.env -f deploy/compose.yaml --profile runner up -d --build
```

Runner Controller 启动与运行期间会持续通过内部回调接口校验运行许可、拉取最新配置与上下文引用；一旦遇到任务暂停、权限变更、许可过期或审批失效，会立即中止容器。

## 6. 审批、后台任务与结果核对

- **统一审批规则**：任务创建（`create_task`）、发送回复、发布知识和各开发阶段共用「设置 → 审批策略」。规则按“禁止 > 人工 > 自动”生效，命中多条自动规则时按更严格的配额执行。表单会根据操作类型自动过滤无关字段，保存时清理旧字段，防止隐藏残留导致策略不命中。
- **审批通知**：每条策略默认开启审批通知，覆盖待审批、自动通过、策略禁止、人工通过/拒绝/撤销以及信息不足的任务建议。可按策略单独关闭或指定内部通知渠道，留空则沿用模块值班渠道（无模块的知识发布使用 `*` 路由）。调整通知开关或渠道不会让已有审批失效；关闭开关只拦截未发出的队列项。
- **后台任务排查**：管理员可在「后台任务」查看失败原因，按需发起重试，或暂时忽略单条/本页失败提醒（忽略仅从概览红点隐藏，可在「已忽略」筛选中恢复或重试）。重试会复用原幂等键，不会绕过暂停、过期审批或外部操作状态机。已过时的开发任务请直接到对应任务详情页恢复或修改目标。
- **外部操作核对（`outcome_unknown`）**：网络超时或进程异常时，发消息、推分支、建 PR 等外部写入可能已在远端生效，状态会标记为「结果待核对」。系统此时**绝不盲目重发**，而是先去远端核查：GitHub 通过任务分支、关联标记和发送者账号核对；飞书若有 `message_id` 可直接查询，仅持本地 UUID 时可能无法自动确认，需到飞书侧人工核实。
- **操作记录标识**：问题详情的时间线、首页动态与「操作记录」页采用统一的来源/状态标签，方便区分用户消息、用户反馈、系统处理、审批和平台操作。值班通知发送失败或结果待核对时，也会在对应问题的时间线留下明确记录。
- **日志脱敏**：运行日志不打印密钥、完整 Token 或原始上游错误报文，错误响应仅返回安全摘要和 `request_id`。

## 7. 冷备份与迁移

迁移或备份时，**数据库、加密主密钥（`encryption_key`）和 `artifacts` 产物目录必须打包在一起**——丢失 `encryption_key` 会导致所有已保存的连接器与模型密钥无法解密。备份包内含敏感凭据，请妥善限制文件权限并存放于安全位置。

当前提供 Linux 冷备份与恢复脚本，操作步骤如下：

1. **停写与停任务**：在 Web 端停止接收新任务，暂停活跃开发任务并确认全部停止。
2. **停止 Runner（如已启用）**：由宿主机管理员手动停止 Runner 专用的用户级 Docker 服务，并卸载 `runtime` 和 `tasks` 挂载点（备份脚本会检查是否已停止，但不会替你修改宿主机 systemd）。
3. **执行备份**：
   ```sh
   sudo script/backup.sh --output /受控目录/agentowl-backup.tar
   ```
   脚本会停止 Compose 服务、核验停机状态后打包数据与配置，保留数字 UID/GID 并生成配套 `.sha256` 校验文件。
4. **准备目标主机并恢复**：在目标机部署同版本源码并留空 `deploy/data`，提前建好与原主机一致的部署 UID/GID（含 Runner 时还需保持原 Runner UID/GID 及 subuid/subgid 映射，并匹配存储驱动）。把归档文件和 `.sha256` 一起拷过去后执行：
   ```sh
   sudo script/restore.sh --archive /受控目录/agentowl-backup.tar
   ```
   恢复前脚本会自动校验 SHA-256、目录结构、账号映射与磁盘余量。
5. **修正路径与重建运行时**：按目标机实际路径更新 Runner 账号 home 目录和 `deploy/.env` 里的 `RUNNER_HOST_DATA_ROOT`，重新运行 `runner-setup.sh` 和 `runner-preflight.sh`（旧 Socket 和 tmpfs 临时工作区不随备份迁移）。如果迁移后还要执行 `make dev`，一并更新 `deploy/data/secrets/dev.env` 中的绝对路径。
6. **核验并恢复服务**：确认域名、身份源与路径无误后，依次运行 `make migrate` 和 `make up`（如需拉起 Runner，请使用第 5.2 节带 `--profile runner` 的启动命令），登录检查问题、知识库、审批和产物下载均正常后，再重新开放外部平台接入。

> 备份和恢复脚本执行完毕后服务会保持停止状态，方便上线前核查。请勿在 PostgreSQL 运行时直接拷贝数据目录，也不要以为停了任务就能跳过数据库停机。
