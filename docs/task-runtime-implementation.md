# 持续任务、统一审批与按需上下文实现记录

本文记录 2026-11-10 至 2026-11-11 期间的核心架构升级、数据迁移和开发机（`10.37.90.168`）发布验收情况。

## 已交付能力

| 模块 | 实现要点 |
| --- | --- |
| 任务状态机 | `taskcore.Decide` 统一收敛创建、修订、暂停、恢复、取消、撤权和阶段推进逻辑；`transitionTask` 负责带版本校验的落库与事件记录，人工操作、Worker、审批失效、设置变更和发布均走同一入口。 |
| 会话路由 | 事件入库时递增线程水位，消费完成后再路由。支持单任务关联多会话（区分主跟进会话与参考会话）、歧义待人工确认、重复投递去重与私聊稳定标识；存在未处理完的来源消息时暂停推进阶段和发布。 |
| 持续输入 | 任务详情页可直接补充信息、勾选纳入新版本，或标记为参考/无关。纳入新输入会生成新修订（revision），旧审批快照保持不变；配置为自动应用范围内补充时同样生成新版本并重新审批。 |
| 任务授权 | 每个修订绑定独立 `mandate`（发起依据、负责人、仓库路径、来源范围与跟进方式）。运行许可和发布前会重查当前权限、规则和来源版本；撤权或来源失效时递增 `epoch`、作废旧审批并停止执行。 |
| 统一审批 | 创建任务（`create_task`）、发送回复、发布知识和所有开发阶段统一收敛到「设置 → 审批策略」与审批列表，均支持人工、自动、禁止及独立通知开关。旧 `/admission` 路径重定向至 `/settings/policies`。 |
| 执行回执 | 锁定输入支持按 Unicode 字符安全分页。执行送达（`delivered`）与进入模型请求（`included`）分开记录，只有成功返回的模型请求才会记入 `included`。回执先在 Runner 本地落盘，随 Inspect 轮询与 Collect 归档幂等回传。 |
| 平台适配 | GitHub、飞书与 Lark 统一接入来源接口，负责事件解析、上下文与附件读取、消息发送和结果核对；Git 对象与 PR 写入继续使用专用发布接口。 |
| 前端与契约 | 补齐任务补充信息、关联会话、跟进模式、统一审批策略与个人中心飞书绑定页面；OpenAPI 契约与 Kiota 客户端保持同步。 |

主要代码入口：[状态规则](../backend/internal/taskcore/task.go)、[任务与输入](../backend/internal/service/task_runtime.go)、[路由与评估](../backend/internal/service/task_routing.go)、[任务创建评估](../backend/internal/service/admission.go)、[授权撤销](../backend/internal/service/task_authority.go)、[平台来源接口](../backend/internal/integration/source.go)、[平台读取实现](../backend/internal/integration/source_read.go)、[Runner 输入与回执](../backend/internal/runner/task_inputs.go)。

## 数据库迁移与协议兼容

- **迁移脚本**（按序追加，不改写历史迁移）：
  - `000010_task_runtime.up.sql`：新增来源线程、任务输入、修订关联、任务授权、评估决策、任务事件和回执表。
  - `000011_runtime_machine_reference.up.sql`：修正 `run_attempts.runtime_machine_id` 外键，使其与实际 `configs` 中的运行机器配置一致；旧表中的独有记录以禁用态保留。
  - `000012_unified_approval_policies.up.sql`：将旧的任务创建规则迁移到统一审批策略（原 `observe` 转人工审批，原 `off` 转停用，保留原 ID 与版本）；旧规则/设置接口退役返回 `410`。
  - `000013`：为已有审批策略默认开启通知并保持原授权版本，不补发历史审批。
  - `000014`：移除任务执行页的开发步骤审批总开关，统一按策略审批（未匹配走人工）；尚未执行的旧总开关审批自动失效。
  - `000015_lark_identity.up.sql`：新增飞书/Lark 登录与账号绑定交易表及会话关联。
- **历史数据回填**：Worker 维护任务每次最多回填 100 条历史来源线程和 100 个旧任务授权记录，不覆盖原有目标、审批和产物；缺少历史路径范围的旧任务会标记缺失，恢复执行前需人工重新确认，且不伪造历史消费回执。
- **协议版本与限额**：
  - Runner 能力新增 `task_input_receipts_v1`、`context_ref_pages_v2` 和 `context_manifest_version: 2`。使用新上下文/输入协议的任务只会调度到声明对应能力的运行机器，不会悄悄降级；旧 RunSpec 字段通过 `omitempty` 保持原摘要兼容。
  - 单条任务输入上限 64,000 字节，单个修订最多采用 128 条输入，超限直接拒绝（可将旧输入改为参考信息）。

## 跨大版本升级注意事项

1. 发布前先确认服务器实际的 Compose project 名、数据卷、TLS 与加密密钥路径，完成数据库、产物和旧镜像备份。
2. 涉及协议或表结构变更时采用停写切换：先暂停新任务领取，确认在跑任务和未知外部操作已收口，先升级全部 Runner，再升级 API、Worker 和 Web（切勿让旧 Worker 与新业务表并发写入）。
3. 若新协议数据已落库后需要回滚，优先回退到仍兼容新协议的构建版本，切勿直接拉起旧 Worker 或覆盖恢复旧数据库备份。
